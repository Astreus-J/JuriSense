# Technology Stack

This is the authoritative, single-page list of every technology used by JuriSense Gate, with a
one-line justification per choice and a link to the ADR (or existing implementation) that decided
it. If a choice is not listed here, it is not approved for use — propose a new ADR instead of
adding a dependency ad hoc. This file is descriptive of decisions made elsewhere (`docs/adr/`); it
does not re-litigate them.

## Backend

| Technology | Role | Why | Decided in |
|---|---|---|---|
| Python 3.13 | Language | Best-in-class ecosystem for document/AI processing (PDF/DOCX parsing, LLM SDKs, OCR bindings) and async I/O for external verification calls; keeps the already-built, already-audited `Accounts` context. | ADR-001 |
| FastAPI | Web framework | Async-first, typed, auto-generates OpenAPI docs (already exposed at `/api/docs`), the framework the existing `Accounts` context is built on. | ADR-001 |
| SQLAlchemy 2.0 (async) + asyncpg | ORM / DB driver | Async-native ORM with a mature migration story (Alembic); asyncpg is the fastest PostgreSQL driver for async Python and is already wired to the external Neon database. | ADR-001, `backend/app/core/db.py` |
| Alembic | Migrations | Standard companion to SQLAlchemy; already in use (`backend/alembic/`). | ADR-001 |
| Pydantic v2 / pydantic-settings | Validation & config | Request/response schemas and typed settings loaded from `.env`, already the pattern in `app/accounts/api/schemas.py` and `app/core/config.py`. | Existing implementation |
| PyJWT | Auth tokens | Stateless JWT access tokens; the library already used for access/refresh token issuance and verification. | ADR-011 |
| Argon2id (argon2-cffi) | Password hashing | OWASP-recommended password hash; already the hashing algorithm for `User.password_hash`. | ADR-011, `docs/auditorias/sprint-01.md` |
| Redis | Cache, rate limiting, revocation, Celery broker | Already provisioned in `docker-compose.yml`; backs the refresh-token revocation blocklist, login-lockout counters, and the Celery broker/result backend. | ADR-011, ADR-006 |
| Celery | Async task queue | Runs short-lived background work (AI extraction jobs, OCR, external verification calls, notification dispatch) without holding long-lived workflow state in the same mechanism. | ADR-006 |
| cel-python (CEL) | Policy rule evaluation | Sandboxed, in-process expression evaluation for the Policy Engine's `when` clauses — no external policy service needed. | ADR-004 |
| json-logic (fallback) | Policy rule compilation target | Alternative compilation target for rules generated by a future no-code rule builder, where a JSON tree is safer to generate than raw CEL text. | ADR-004 |
| uv | Dependency management | Fast, lockfile-based Python dependency manager already used for the backend (`uv sync`, `uv run`, `uv.lock`). | Existing implementation |
| ruff | Lint & format | Single fast tool for lint + format (replaces flake8/isort/black); already configured in `backend/pyproject.toml`. | Existing implementation |
| pytest + pytest-asyncio | Test runner | Async-native test runner, already the standard for `backend/tests/`. | Existing implementation |
| httpx (ASGITransport) | Integration test client | Drives the FastAPI app in-process without a real network socket, already the pattern in `backend/tests/conftest.py`. | Existing implementation |
| fakeredis / aiosqlite | Test doubles | In-memory Redis and SQLite substitutes so integration tests need no external services, already used in `conftest.py`. | Existing implementation |

## Data

| Technology | Role | Why | Decided in |
|---|---|---|---|
| PostgreSQL (external, Neon-managed) | Primary database | Managed Postgres removes operational burden from the single-VPS hosting model; already the database behind `DATABASE_URL` in `backend/.env`. | Existing implementation, `docs/00-project/overview.md` |
| pgvector | Vector search extension | Adds embeddings storage/similarity search directly inside the already-provisioned Postgres, avoiding a standalone vector database at current data volume. | ADR-009 |
| Postgres `tsvector` | Full-text search | Combined with `pgvector` for hybrid (vector + keyword + metadata) retrieval over the policy/contract corpus. | ADR-009 |

## Infrastructure

| Technology | Role | Why | Decided in |
|---|---|---|---|
| Docker Compose | Local dev orchestration | Runs frontend, backend, and Redis with hot reload and named volumes shadowing build artifacts; the existing dev workflow. | `docker-compose.yml`, `docs/07-engineering/development-workflow.md` |
| Single VPS + Docker Compose | Production hosting | Only the database and AI provider APIs are external; frontend, backend, Celery workers, Redis, and Nginx run on one VPS, fronted by Cloudflare (CDN/WAF). | `docs/00-project/overview.md` |
| Cloudflare R2 (S3-compatible) | Object storage (prod) | Zero-egress-fee S3-compatible storage for contracts/evidence, with per-organization key prefixes and bucket versioning for immutability. | ADR-008 |
| MinIO (S3-compatible) | Object storage (dev) | Local, S3-API-compatible stand-in for R2 so the storage abstraction is exercised identically in development and production. | ADR-008 |
| GitHub Actions | CI/CD | Consistent with `gh` CLI already used for this project's GitHub workflow; runs lint/test/security/build stages before deployment. | `docs/07-engineering/ci-cd.md` |

## AI

| Technology | Role | Why | Decided in |
|---|---|---|---|
| OpenAI API | LLM provider (primary/fallback, per task) | Structured-output (JSON schema / tool-calling) extraction of contract/supplier data, selected per task via the AI Gateway abstraction. | ADR-005 |
| Anthropic Claude API | LLM provider (primary/fallback, per task) | Second provider behind the same AI Gateway interface, giving automatic fallback on error/timeout and avoiding single-provider lock-in. | ADR-005 |
| pgvector (shared with Data) | Embeddings store | RAG retrieval over the policy playbook and contract corpus reuses the same Postgres instance — no separate vector DB. | ADR-009 |

**Status: TBD** — exact model selection per task (extraction vs. classification vs. summarization)
and the API-cost threshold that would trigger evaluating self-hosted open-weight models.
**Current preferred option:** keep both providers API-first, selecting per task via config.
**Why undecided:** no real extraction volume/accuracy data exists yet to justify a specific model
pin or a self-hosting business case. **Resolution:** revisit once production extraction volume and
per-document cost data exist. **Decision artifact:** `docs/05-ai/ai-strategy.md`.

## Blockchain / Trust Layer

| Technology | Role | Why | Decided in |
|---|---|---|---|
| `AnchoringProvider` interface | Provider-agnostic abstraction | All blockchain interaction goes through `submit_hash()` / `get_proof()` / `verify()`; no code depends on a specific chain SDK. | ADR-007 |

**Status: TBD** — the concrete `AnchoringProvider` adapter (Constellation Network, an EVM-compatible
L2 testnet such as Base Sepolia/Polygon Amoy, or ICP/Caffeine AI).
**Current preferred option:** Constellation Network first (best conceptual fit and confirmed
hackathon sponsor), EVM L2 testnet as the safest fallback.
**Why undecided:** the Phase 8 technical spike (SDK maturity, integration effort, transaction cost)
has not run yet. **Resolution:** the spike concludes with a chosen default adapter; the interface
above does not change regardless of outcome. **Decision artifact:** ADR-007,
`docs/06-blockchain/anchoring-providers.md`.

## Cross-cutting notes

- Every entry above is either already implemented (`backend/`, `frontend/`, `docker-compose.yml`) or
  locked by an ADR. Introducing a new library/service requires a new ADR, not a silent
  `pyproject.toml`/`package.json` addition — see `docs/adr/` for the ADR template and process.
- Per the project-wide English-only rule (`docs/07-engineering/coding-standards.md`), all new code
  written against this stack — identifiers, schemas, migrations, tests, logs — is English, even
  where the underlying library or provider documentation is not.
